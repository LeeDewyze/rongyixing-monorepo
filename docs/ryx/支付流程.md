# 支付流程

本文记录当前 H5/Web 从预订提交到支付、支付结果、订单详情或订单列表的实际流程，供联调、抓包和问题排查使用。

## 1. 术语与分流

当前代码使用 `channel` 区分业务轨道：

| channel | 业务含义 | 订单类型 |
| --- | --- | --- |
| `tmc` | 因公、公户、企业差旅 | 企业订单 |
| `tourist` | 因私、私户、个人出行 | 个人订单 |

`PayType` 是支付责任或支付渠道，不等同于 `channel`。例如因公订单也可能选择个付；因私订单则使用私户支付接口。

当前模式转换位于 `apps/h5/src/lib/flight-travel-mode.ts` 和对应 Web 文件：

```text
business -> channel=tmc -> TravelType=1
personal -> channel=tourist -> TravelType=2
```

## 2. 预订提交后的公共流程

机票、酒店、火车的提交流程都遵循以下顺序：

```text
预订页
  -> 提交预订接口
  -> 从响应中解析 OrderId
  -> 按 IsCheckPay / TradeNo / PayType 判断下一步
  -> 清理预订页临时状态
  -> replace 跳转
  -> 支付页、订单详情或订单列表
```

提交成功后会设置 `isLeavingAfterSubmit`，展示 `BookingSubmitTransition`。该页面只是提交成功到下一路由之间的视觉过渡，不负责支付确认，也不额外等待接口。

过渡组件：

```text
packages/ui/src/components/booking/booking-submit-transition.tsx
```

预订页会清理选人、舱位、酒店房型、改签等页面临时状态，然后通过 React Router 的 `navigate(..., { replace: true })` 离开预订页。订单号主要通过 URL 和 navigation state 传递，不需要为普通同页跳转单独写入 storage。

## 3. 因公机票

### 3.1 提交后分流

代码位置：`apps/h5/src/pages/flight/FlightBookPage.tsx`，Web 端对应页面逻辑一致。

```text
提交机票订单
  -> 取得 OrderId
  -> 如果 IsCheckPay=true 且有 TradeNo，轮询 CheckPay
     最多 5 次，每次间隔 3 秒
  -> 根据 PayType 决定下一步
```

结果：

| 条件 | 下一步 |
| --- | --- |
| 公付 | 过渡页后 replace 到机票订单详情 |
| 个付/授信付 | 过渡页后 replace 到机票支付页 |
| 没有 OrderId | 过渡页后进入订单列表 |
| 改签提交成功 | 直接进入订单详情，不走普通支付页 |

支付页路径：

```text
H5:  /flight/pay/{orderId}
Web: /orders/flight/{orderId}/pay
```

### 3.2 因公机票支付

请求轨道：

```text
TmcApiOrderUrl-Pay-GetTotalPayAmount
TmcApiOrderUrl-Order-GetOrderPays
TmcApiOrderUrl-Pay-Create
TmcApiOrderUrl-Pay-Process
```

支付页加载订单详情、应付金额和可用支付方式。点击支付后：

```text
Pay-Create
  -> 返回 PayUrl/Url：整页跳转外部支付
  -> 没有 PayUrl 但有 OutTradeNo：调用 Pay-Process
  -> Pay-Process 成功：replace 到订单详情
  -> 没有交易号：提示已提交，后续到订单中查看
```

## 4. 因公酒店

代码位置：`apps/h5/src/pages/hotel/HotelBookPage.tsx` 和 Web 对应页面。

```text
酒店提交
  -> 取得 OrderId
  -> 如果 IsCheckPay=true 且有 TradeNo，轮询 CheckPay
  -> 个付条件满足：过渡页后进入支付页
  -> 否则：过渡页后 replace 到酒店订单详情
```

支付页路径：

```text
H5:  /hotel/pay/{orderId}
Web: /orders/hotel/{orderId}/pay
```

因公酒店使用公户支付方法：

```text
TmcApiOrderUrl-Pay-Create
TmcApiOrderUrl-Pay-Process
```

酒店订单处于 `Booking`、`WaitHandle` 或 `WaitPay` 等过渡状态时，订单详情页会继续轮询，直到状态稳定或后端停止返回轮询条件。

## 5. 因公火车

代码位置：`apps/h5/src/pages/train/TrainBookPage.tsx` 和 Web 对应页面。

```text
火车提交
  -> 取得 OrderId
  -> 如果 IsCheckPay=true 且有 TradeNo，轮询 CheckPay
  -> 因公且支付条件满足：过渡页后进入火车支付页
  -> 其他情况：过渡页后进入订单详情
```

支付页路径：

```text
H5:  /train/pay/{orderId}
Web: /orders/train/{orderId}/pay
```

火车订单可能先处于待确认、待出票状态。订单详情页会继续轮询，并可能展示确认出票等操作，因此“提交成功”不一定表示已经完成出票。

## 6. 因私机票

因私机票的订单和支付使用 `channel=tourist`：

```text
提交机票订单
  -> 取得 OrderId
  -> 过渡页
  -> /flight/pay/{orderId}?channel=tourist
  -> 私户支付
```

请求轨道：

```text
TmcTouristOrderUrl-Order-GetOrderPays
TmcTouristOrderUrl-Pay-GetTotalPayAmount
TmcTouristOrderUrl-Pay-Create
TmcTouristOrderUrl-Pay-Process
```

支付方式分两类：

### 微信内浏览器

```text
没有 openid
  -> 微信 OAuth
  -> 回到支付页

有 openid
  -> Pay-Create，CreateType=JsSdk，DataType=json
  -> 微信 JS-SDK 调起支付
  -> Pay-Process
  -> replace 到订单详情
```

### 非微信环境的微信或支付宝

```text
保存 ryx_pending_pay_context
  -> 整页跳转 /home/Pay
  -> 外部支付页面
  -> 支付完成后回到应用/后端回调地址
```

当前 `ryx_pending_pay_context` 使用 `sessionStorage` 保存支付方式、业务轨道和产品类型，TTL 为 15 分钟。它只用于跨整页跳转恢复支付上下文，不是订单数据存储。

支付宝没有前端微信式的支付结果确认标记，最终状态以服务端和订单详情为准。

## 7. 因私酒店

因私酒店使用独立的私户酒店支付方法：

```text
提交酒店订单
  -> 取得 OrderId
  -> 过渡页
  -> /hotel/pay/{orderId}?channel=tourist
  -> 私户酒店支付
```

支付接口：

```text
TmcTouristHotelUrl-Pay-Create
TmcTouristHotelUrl-Pay-Process
```

H5 支付完成后进入：

```text
/hotel/result/{orderId}
```

结果页根据订单状态显示继续支付、正在确认订单或订单信息。Web 端主要直接进入：

```text
/orders/hotel/{orderId}
```

## 8. 因私火车

当前因私火车与因私机票、酒店不同：

```text
提交火车订单
  -> 取得 OrderId
  -> 过渡页
  -> /orders/train/{orderId}?channel=tourist
```

当前代码在火车提交后的支付判断中限制了 `productChannel !== "tourist"`，因此因私火车不会从预订页进入前端支付页，而是直接进入订单详情，由订单详情页展示订单状态和后续操作。

## 9. 支付页公共加载与支付接口

支付页进入后会并行准备：

```text
订单详情
应付金额
可用支付方式
```

对应 Hook：

```text
apps/h5/src/hooks/useOrderPay.ts
apps/web/src/hooks/useOrderPay.ts
```

支付接口抽象位于 `packages/api/src/apis/pay.ts`：

| 能力 | 因公 | 因私 |
| --- | --- | --- |
| 应付金额 | `TmcApiOrderUrl-Pay-GetTotalPayAmount` | `TmcTouristOrderUrl-Pay-GetTotalPayAmount` |
| 支付方式 | `TmcApiOrderUrl-Order-GetOrderPays` | `TmcTouristOrderUrl-Order-GetOrderPays` |
| 创建支付 | `TmcApiOrderUrl-Pay-Create` | `TmcTouristOrderUrl-Pay-Create`，因私酒店使用 `TmcTouristHotelUrl-Pay-Create` |
| 处理支付 | `TmcApiOrderUrl-Pay-Process` | `TmcTouristOrderUrl-Pay-Process`，因私酒店使用 `TmcTouristHotelUrl-Pay-Process` |

支付倒计时使用后端返回的 `PayHoldTime`。前端负责显示倒计时，支付是否过期最终由后端在创建支付或订单操作时判断。

## 10. 支付完成后的落点

### SPA 内完成支付

```text
Pay-Create
  -> Pay-Process
  -> navigate(..., { replace: true })
  -> 订单详情或结果页
```

这种方式不离开新版 SPA，订单号通过路由传递。

### 整页外部支付

```text
支付页
  -> 保存 ryx_pending_pay_context
  -> window.location.assign(PayUrl)
  -> 离开新版 SPA
  -> 外部支付
  -> 返回应用或回调地址
```

微信 legacy 回跳可能携带：

```text
wechatPayResultNumber={OutTradeNo}
```

应用启动阶段由 `apps/h5/src/lib/pay-result-callback.ts` 或 Web 对应文件读取该参数，然后调用 `Pay-Process`。确认成功后清理：

```text
ryx_pending_pay_context
wechatPayResultNumber
```

确认失败时保留上下文和参数，允许刷新后再次尝试；支付本身是否成功仍以服务端订单状态为准。

## 11. 详情页与列表页

订单详情页按产品分别请求订单详情：

```text
机票：Order-Detail 对应公户/私户方法
火车：Order-Detail 对应公户/私户方法
酒店：Order-Detail 对应公户/私户方法
```

详情页根据订单状态决定是否显示支付、取消、确认出票、改签或退款等操作。点击返回时通常回到对应的订单列表，并保留 `channel` 和列表筛选条件。

订单号缺失或无法解析时，不进入不存在的详情 URL，降级到订单列表：

```text
H5:  /home/orders?tab=...
Web: /orders?tab=...
```

订单列表根据 `channel`、产品 tab 和 scope 调用对应的订单列表接口。支付完成后返回列表时，列表会重新请求并以服务端最新状态展示订单。

## 12. 场景总表

| 场景 | 提交后 | 支付轨道 | 最终落点 |
| --- | --- | --- | --- |
| 因公机票公付 | 过渡页 | 无前端支付 | 机票订单详情 |
| 因公机票个付/授信付 | 过渡页 | `TmcApiOrderUrl` | 机票支付页，再到详情 |
| 因公酒店公付 | 过渡页 | 无前端支付 | 酒店订单详情 |
| 因公酒店个付 | 过渡页 | `TmcApiOrderUrl` | 酒店支付页，再到详情 |
| 因公火车 | 过渡页 | 按 `CheckPay` 和 `PayType` 判断 | 支付页或订单详情 |
| 因私机票 | 过渡页 | `TmcTouristOrderUrl`，必要时 `/home/Pay` | 支付完成后订单详情 |
| 因私酒店 | 过渡页 | `TmcTouristHotelUrl` | 结果页或订单详情 |
| 因私火车 | 过渡页 | 当前不从预订页进入支付页 | 火车订单详情 |
| 任意产品缺少 OrderId | 过渡页 | 无法继续详情 | 对应订单列表 |

## 13. 排查时重点记录

抓包或 vConsole 排查支付问题时，建议按顺序记录：

1. 预订接口的 `channel`、`OrderId`、`IsCheckPay`、`TradeNo`、`PayType`。
2. 是否展示过 `BookingSubmitTransition`，以及之后实际跳转的路由。
3. 支付页请求使用的产品类型和 `channel`。
4. `GetTotalPayAmount`、`GetOrderPays`、`Pay-Create`、`Pay-Process` 的实际 Method 和请求参数。
5. `Pay-Create` 是否返回 `PayUrl`/`Url`、`OutTradeNo`，以及是否发生整页跳转。
6. 外部支付返回后是否存在 `wechatPayResultNumber`，`sessionStorage` 中的 `ryx_pending_pay_context` 是否未过期。
7. 最终以订单详情接口返回的服务端状态确认出票、支付和订单处理结果。
